# ADR-0005：不在 Windows 上自举交叉工具链，优先预构建 + CI 分发

- **状态**：已接受
- **日期**：2026-02
- **相关**：DESIGN.md §13 工具链获取策略、DEPENDENCIES.md §1

## 背景

OSDev 的第一道门槛就是工具链。本机实测（`Get-Command` 探测）：
`cmake`、`ninja`、`qemu-system-x86_64`、`gcc`、`clang`、`nasm` **全部缺失**。
这不是个例，而是目标用户的常态。

候选路线有三条：

1. 在用户机器上从源码编译交叉工具链（binutils + GCC + newlib）；
2. 要求用户自行安装（文档里写一堆环境配置步骤）；
3. 用预构建二进制，必要时在我们的 CI 上编译后分发。

## 决策

**路线 3。** 具体分级：

1. **优先探测本机**：项目配置显式路径 → 用户配置 → 应用托管目录 `%LOCALAPPDATA%\MetalForge\tools\`
   → `PATH` → 常见安装位置白名单。命中即用，并在"工具链健康"面板显示来源与版本。
2. **引导用户获取**：给出官方下载页、SHA256、建议安装目录；对可解压的 zip 型工具
   （NASM、CMake、Ninja）提供应用内下载 + 校验 + 解压到托管目录，需用户点击、带进度与取消。
3. **CI 构建分发**：`xorriso`、`iasl`、`openocd` 这类小型工具，用 GitHub Actions 的 Linux runner
   交叉构建出 Windows 产物，作为 Release 附件；本地 `scripts/build-tools.ps1` 走 MSYS2 作为备选。
4. **绝不做**：静默下载、静默执行安装程序、修改系统级 `PATH`（只改进程环境或记录到用户配置）。

### 明确不做的事

**不在 Windows 上从源码自举 binutils + GCC 交叉工具链。**
理由：单次构建以小时计、依赖 MSYS2 环境、失败模式极多（路径长度、shell 差异、依赖包版本），
而产出与预构建二进制相比没有实质优势。这是"投入产出比明确为负"的选项。

## 后果

**正面**
- 用户侧的时间成本从"数小时甚至数天"降到"点几下"。
- 所有获取路径集中在 `assets/targets/toolchains.json`，改来源不用改代码。
- 工具缺失不再表现为一串英文报错，而是"缺少 X，点这里获取"（G-01）。

**负面 / 风险**
- **依赖第三方预构建来源的持续性**（DESIGN.md 风险 R4）。
  缓解：在配置里登记多个候选源 + SHA256；CI 自建流水线作为兜底；来源变更只改 JSON。
- 应用内下载意味着网络与磁盘写入，需要明确的用户确认与进度反馈。
  缓解：默认不自动下载；下载后必须校验哈希并跑 `--version` 验证，失败即回滚且不留半成品。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| Windows 上源码自举交叉工具链 | 单次数小时、失败模式多、产出无优势；用户等不起 |
| 要求用户自行安装并写文档 | 与"让 OSDev 像写普通 C 程序一样可控"的愿景直接冲突；新手会在第一步流失 |
| 随 IDE 打包全部工具链 | 体积从几十 MB 涨到数 GB（GCC + QEMU + LLVM + QEMU 固件）；许可与再分发审查成本高 |
| WebAssembly 版工具链 | 性能与系统调用能力都不足以编译内核 |
